# Technical Design Document

## Expense & Budget Visualizer

**Feature name:** `expense-budget-visualizer`
**Workflow:** Requirements-First
**Source of truth:** `requirements.md`

---

## Overview

The Expense & Budget Visualizer is a single-page, client-side web application built with plain HTML, CSS, and Vanilla JavaScript. It runs entirely in the browser — no server, no build tools, no framework. Users record expense transactions by filling in a form, view their transaction history in a scrollable list, see a running total, and observe a pie chart that breaks spending down by category. All data is saved to `localStorage` and reloaded on the next visit.

The project is intentionally simple. The goal is a clean, readable codebase that a beginner can follow and extend over roughly five days of work.

**Technology stack:**

| Concern | Solution |
|---|---|
| Markup | HTML5 (single `index.html`) |
| Styles | CSS3 (`css/style.css`) |
| Logic | Vanilla JavaScript ES6+ (`js/script.js`) |
| Chart | Chart.js loaded from CDN |
| Persistence | `localStorage` API, key `"expense_transactions"` |
| Hosting | Open `index.html` directly in a modern browser |

---

## Architecture

The application has no build step and no module system. Everything is loaded by the browser when `index.html` is opened. The architecture is a straight-line event-driven model:

```
User Action
    │
    ▼
Event Listener (in js/script.js)
    │
    ▼
Validate / Mutate in-memory array (transactions[])
    │
    ▼
Write to localStorage
    │
    ├──► Failure → Rollback mutation + show error
    │
    └──► Success
            │
            ├──► Re-render Transaction List (DOM)
            ├──► Recalculate and re-render Total Display (DOM)
            └──► Update Chart.js pie chart instance
```

There is one central in-memory array (`transactions`) that is the single source of truth. Every UI update reads from that array. `localStorage` is written to after every mutation (add or delete) and read once on page load.

### File layout

```
index.html          ← HTML structure, CDN script tag, link to css/style.css and js/script.js
css/
  style.css         ← All styles, organised by section comment
js/
  script.js         ← All JavaScript logic, organised by section comment
```

No other files are required. `index.html` must not contain inline `<style>` blocks or inline `<script>` blocks (other than the Chart.js CDN tag).

### Script loading order (Requirement 10.3)

```html
<!-- inside <head> or at end of <body> -->
<script src="https://cdn.jsdelivr.net/npm/chart.js"></script>
<script src="js/script.js"></script>
```

Chart.js must appear **before** `js/script.js` so that the global `Chart` constructor is available when the app initialises.

## Components and Interfaces

### HTML page structure

`index.html` contains one `<main>` element with three logical sections that stack in the DOM:

```
<main>
  ├── <section id="form-section">      ← Expense_Form (Req 1)
  ├── <section id="list-section">      ← Transaction_List + Total_Display (Req 4, 5, 6)
  └── <section id="chart-section">     ← Chart canvas + empty placeholder (Req 7)
</main>
```

#### 1. Expense Form (`#form-section`)

```
<form id="expense-form">
  ├── Item name field
  │     <label> + <input type="text" id="item-name" maxlength="100">
  │     <span class="error" id="name-error">  ← inline error (Req 2.1)
  │
  ├── Amount field
  │     <label> + <input type="number" id="amount" step="0.01" min="0">
  │     <span class="error" id="amount-error"> ← inline error (Req 2.2–2.5)
  │
  ├── Category selector
  │     <label> + <select id="category">
  │       <option value="">-- Select category --</option>
  │       <option value="Food">Food</option>
  │       <option value="Transport">Transport</option>
  │       <option value="Fun">Fun</option>
  │     </select>
  │     <span class="error" id="category-error"> ← inline error (Req 2.6)
  │
  └── <button type="submit">Add Expense</button>
```

The `<form>` element uses `submit` event (not a click handler on the button), so both mouse click and Enter key trigger the same handler (Requirement 3.5).

#### 2. Summary bar (`#list-section` header)

```
<div id="summary">
  <h2>Transactions</h2>
  <p>Total: <span id="total-display">$0.00</span></p>
</div>
```

`#total-display` is updated by JavaScript on every add/delete (Req 6).

#### 3. Transaction List (`#transaction-list`)

```
<ul id="transaction-list">
  <!-- Empty state (shown when no transactions) -->
  <li id="empty-message">No expenses added yet.</li>

  <!-- Per transaction (generated by JS) -->
  <li data-id="{id}">
    <span class="item-name">{name}</span>
    <span class="item-category">{category}</span>
    <span class="item-amount">${amount}</span>
    <button class="delete-btn" data-id="{id}" aria-label="Delete {name}">Delete</button>
  </li>
</ul>
```

`data-id` on both the `<li>` and the delete `<button>` lets the event handler identify which transaction to remove.

#### 4. Chart section (`#chart-section`)

```
<section id="chart-section">
  <canvas id="expense-chart"></canvas>
  <p id="chart-placeholder">No spending data available.</p>
</section>
```

When there are no transactions, the `<canvas>` is hidden (`display: none`) and `#chart-placeholder` is shown. When transactions exist, the reverse applies (Req 7.5).

#### 5. Error notification area

```
<div id="storage-error" role="alert" aria-live="polite"></div>
```

Used for non-blocking storage write failure messages (Req 5.6). Positioned fixed or at the top of the page, styled as a dismissible banner.


**Desktop layout (≥ 600px):** A single-column layout with a constrained `max-width` centered on the page. The form, transaction list, and chart are displayed vertically in document order. This keeps the layout simple, readable, and easy to maintain.

**Mobile layout (< 600px, Req 9.3):** The form, transaction list, and chart stack vertically in document order inside a single-column layout. No horizontal scrolling at 320 px or wider (Req 9.1).

**Touch targets (Req 9.2):** All interactive controls (`<button>`, `<input>`, `<select>`) must have a minimum rendered size of 44 × 44 CSS pixels on viewports below 600 px. Achieved with:

```css
@media (max-width: 599px) {
  input, select, button {
    min-height: 44px;
    min-width: 44px;
  }
}
```

**Chart resize (Req 9.4):** The `<canvas>` is wrapped in a container div with `width: 100%`. Chart.js is initialised with `responsive: true` and `maintainAspectRatio: true`. This makes the chart resize automatically when the viewport changes.

**Transaction list scrolling (Req 4.2):** `#transaction-list` is given a fixed `max-height` and `overflow-y: auto`.

**Inline errors (Req 2):** `.error` spans are `display: block`, `color: red`, `font-size: 0.85rem`. They are empty strings by default; JavaScript sets their `textContent` to show or clear messages.

## Data Models

### Transaction object

A transaction is a plain JavaScript object:

```js
{
  id: string,       // unique identifier — e.g. String(Date.now()) + Math.random().toString(36).slice(2)
  name: string,     // trimmed item name, 1–100 characters
  amount: number,   // positive number, rounded to 2 decimal places at creation time
  category: string  // one of: "Food" | "Transport" | "Fun"
}
```

### In-memory state

```js
let transactions = [];  // the single source of truth; populated on init from localStorage
```

`transactions` is a module-level (top-of-file) `let` variable. All functions read from and write to this array.

### localStorage schema

The array is stored as a JSON string under a single key:

```
Key:   "expense_transactions"
Value: JSON.stringify(transactions)
       e.g. '[{"id":"1720000000000abc","name":"Coffee","amount":3.50,"category":"Food"}]'
```

## Form Validation and Submission Flow

### Validation rules (Requirement 2)

All validation runs inside a `validateForm()` function that returns `true` if all fields pass or `false` if any fail. It sets error message text on the relevant `<span class="error">` elements as a side effect.

| Field | Condition | Error message |
|---|---|---|
| Item name | Empty after trim | "Item name is required." |
| Amount | Empty | "Amount is required." |
| Amount | Non-numeric | "Amount must be a valid number." |
| Amount | ≤ 0 | "Amount must be greater than zero." |
| Amount | > 2 decimal places | "Amount must have at most 2 decimal places." |
| Category | No option selected (value is `""`) | "Please select a category." |

All fields are checked in a single pass. All applicable error `<span>` elements are updated before the function returns — so multiple errors display simultaneously (Req 2.7). When a field passes, its error `<span>` is cleared (Req 2.8).

**Decimal place check:** Use a regex such as `/^\d+(\.\d{1,2})?$/` on the raw string value of the amount input to catch values with more than 2 decimal places before converting to a number.

### Submission flow (Requirement 3)

```
form 'submit' event fires
    │
    ▼
event.preventDefault()
    │
    ▼
validateForm()
    ├── returns false → stop (errors already shown)
    └── returns true
            │
            ▼
        createTransaction(name, amount, category)
            │
            ▼
        transactions.unshift(newTransaction)   ← prepend to array
            │
            ▼
        saveToStorage()
            │
            ▼
        renderTransactionList()
        updateTotal()
        updateChart()
            │
            ▼
        resetForm()
```

`resetForm()` clears the item name field, clears the amount field, resets the category selector to the placeholder, and clears all error spans.

## Add and Delete Transaction Flow

### Add transaction (Requirements 3, 4, 6, 7, 8)

1. `createTransaction(name, amount, category)` — builds the plain object with a generated `id`.
2. `transactions.unshift(newTransaction)` — prepends to the in-memory array.
3. `saveToStorage()` — writes the updated array to `localStorage`.
4. `renderTransactionList()` — rebuilds the `<ul>` from scratch (see Render Functions below).
5. `updateTotal()` — recalculates and writes to `#total-display`.
6. `updateChart()` — updates the Chart.js instance (see Chart section below).
7. `resetForm()` — clears all form fields.

### Delete transaction (Requirements 5, 6, 7, 8)

The `#transaction-list` element has a single delegated `click` event listener. When the event target matches `.delete-btn`, the `data-id` attribute is read.

```
click event on #transaction-list
    │
    ▼
  Delete click
    ↓
  Find transaction
    ↓
  Filter transaction from array
    ↓
  saveToStorage()
    ↓
  Success → render list + total + chart
  Failure → rollback transaction array + show error

```

If `saveToStorage()` fails (the `try/catch` catches a `QuotaExceededError` or other exception), the transaction is **not removed** from the in-memory array, the UI is not updated, and a non-blocking error message is shown in `#storage-error` (Req 5.6).

## Total Spending Calculation and Update Flow

`updateTotal()` is a pure rendering function:

```
sum = transactions.reduce((acc, t) => acc + t.amount, 0)
formatted = '$' + sum.toFixed(2)
document.getElementById('total-display').textContent = formatted
```

It is called after every add and every successful delete. When `transactions` is empty, `sum` is `0` and the display shows `$0.00` (Req 6.4).

## Chart.js Pie Chart Rendering and Update Flow

### Initial creation

On page load (during `init()`), after loading transactions from storage, the chart is created once:

```js
const ctx = document.getElementById('expense-chart').getContext('2d');
let chartInstance = new Chart(ctx, {
  type: 'pie',
  data: buildChartData(),
  options: {
    responsive: true,
    maintainAspectRatio: true,
    plugins: {
      legend: { display: true }
    }
  }
});
```

`chartInstance` is stored in a module-level variable so `updateChart()` can access it.

### `buildChartData()`

Produces the Chart.js `data` object from the current `transactions` array:

```
categories = ["Food", "Transport", "Fun"]
totals     = sum of amounts per category (0 if no transactions in that category)

Return:
  {
    labels: [categories with total > 0],
    datasets: [{
      data:            [totals for categories with total > 0],
      backgroundColor: [one colour per category — fixed colour map]
    }]
  }
```

Fixed colour map (consistent with the legend, Req 7.1):

```js
const CATEGORY_COLORS = {
  Food:      '#FF6384',
  Transport: '#36A2EB',
  Fun:       '#FFCE56'
};
```

Categories with a total of zero are **excluded** from labels and data arrays (Req 7.6).

### `updateChart()`

Never destroys and recreates the chart instance. Instead, it mutates the existing instance's data and calls `update()`:

```js
function updateChart() {
  const data = buildChartData();

  if (transactions.length === 0) {
    document.getElementById('expense-chart').style.display = 'none';
    document.getElementById('chart-placeholder').style.display = 'block';
    chartInstance.data.labels = [];
    chartInstance.data.datasets[0].data = [];
    chartInstance.update();
    return;
  }

  document.getElementById('expense-chart').style.display = 'block';
  document.getElementById('chart-placeholder').style.display = 'none';
  chartInstance.data.labels = data.labels;
  chartInstance.data.datasets[0].data = data.data;
  chartInstance.data.datasets[0].backgroundColor = data.backgroundColor;
  chartInstance.update();
}
```

This approach avoids canvas teardown/recreation and the "canvas already in use" warning from Chart.js (Req 7.3, 7.4).

## localStorage Persistence

### Save (`saveToStorage()`)

```js
function saveToStorage() {
  try {
    localStorage.setItem('expense_transactions', JSON.stringify(transactions));
  } catch (e) {
    throw e;  // caller decides how to handle (add vs delete contexts differ)
  }
}
```

Called after every mutation (Req 8.1, 8.2). The caller wraps the call in `try/catch` when error recovery is needed (e.g., delete flow).

### Load (`loadFromStorage()`)

Called once inside `init()`:

```js
function loadFromStorage() {
  try {
    const raw = localStorage.getItem('expense_transactions');
    if (raw === null) return [];
    const parsed = JSON.parse(raw);
    if (!Array.isArray(parsed)) return [];
    return parsed;
  } catch (e) {
    console.warn('expense_transactions: failed to parse stored data.', e);
    return [];
  }
}
```

Handles all three failure modes from Req 8.6:
- Key absent → `getItem` returns `null` → returns `[]`.
- Value is `null` literal in storage → same path.
- Value fails `JSON.parse` → caught, console warning, returns `[]`.
- Parsed value is not an array → returns `[]`.

In all failure cases, the app initialises with an empty array and renders the empty state (Req 8.6).

## Render Functions

### `renderTransactionList()`

Rebuilds the entire `<ul>` content from scratch on every call. This is the simplest, most readable approach for a beginner project.

```
if transactions is empty:
    show #empty-message (Req 4.3)
    return

hide #empty-message
for each transaction in transactions:
    create <li data-id="{id}">
      <span class="item-name">{name}</span>
      <span class="item-category">{category}</span>
      <span class="item-amount">${amount.toFixed(2)}</span>
      <button class="delete-btn" data-id="{id}" aria-label="Delete {name}">Delete</button>
    append <li> to #transaction-list
```

Amount is formatted with `.toFixed(2)` and prefixed with `$` (Req 4.1).

### `updateTotal()`

See "Total Spending Calculation" section above.

### `updateChart()`

See "Chart.js Pie Chart Rendering" section above.

### `showStorageError(message)`

```
#storage-error.textContent = message
#storage-error.style.display = 'block'
// Optional: auto-hide after 5 seconds
setTimeout(() => { #storage-error.style.display = 'none'; }, 5000);
```

Styled as a non-blocking banner (Req 5.6). Uses `role="alert"` and `aria-live="polite"` for accessibility.

## Error Handling

### Validation errors (Requirement 2)

Inline, adjacent to each field. Shown by writing to the field's `<span class="error">`. Cleared when the field passes. Multiple errors are shown simultaneously.

### localStorage parse failure on init (Requirement 8.6)

Caught in `loadFromStorage()`. App initialises with empty array. Console warning is logged. No user-visible error is shown — the empty state UI handles this gracefully.

### localStorage write failure on add (Requirement 3, implied)

`saveToStorage()` is called before rendering after an add. If it throws:

```
try {
  saveToStorage();
} catch (e) {
  // For add: the transaction was already unshifted into memory.
  // Remove it and show an error.
  transactions.shift();
  showStorageError('Could not save your transaction. Storage may be full.');
  return;
}
// Only reach here if save succeeded
renderTransactionList();
updateTotal();
updateChart();
```

### localStorage write failure on delete (Requirement 5.6)

```
const previousTransactions = transactions;
transactions = transactions.filter(t => t.id !== id);

try {
  saveToStorage();
} catch (e) {
  transactions = previousTransactions;
  showStorageError('Could not save the deletion. Please try again.');
  return;
}

// Only reach here if save succeeded
renderTransactionList();
updateTotal();
updateChart();
```

The transaction remains in the list and in the in-memory array.

## Correctness Properties

**Note:** The following correctness properties are stated as observable invariants that the application must always satisfy during normal use. They are verified through manual smoke testing in the browser.

### Property 1: Total consistency

**Validates: Requirements 6.1, 6.2, 6.3, 6.4**

The value displayed in `#total-display` always equals `$` followed by the sum of all `amount` fields in the in-memory `transactions` array, formatted to two decimal places. When the array is empty, the display shows `$0.00`.

### Property 2: Chart consistency

**Validates: Requirements 7.1, 7.2, 7.3, 7.4, 7.6**

The pie chart segments and their values always reflect the per-category totals computed from the in-memory `transactions` array. Categories with a total of zero are excluded. The chart is updated immediately after every add and every successful delete.

### Property 3: Storage consistency

**Validates: Requirements 8.1, 8.2, 8.3**

The JSON string stored under the key `"expense_transactions"` in `localStorage` always matches `JSON.stringify(transactions)` after every mutation. The storage write always occurs before any UI update so that the persisted state and the rendered state cannot diverge.

### Property 4: Delete atomicity

**Validates: Requirements 5.2, 5.5, 5.6**

A transaction is removed from the UI and from the in-memory array if and only if the corresponding `localStorage` write succeeds. If the write fails, the transaction is retained in both the array and the rendered list; no partial deletion is observable to the user.

### Property 5: Empty-state exclusivity

**Validates: Requirements 4.3, 7.5**

The empty-state placeholder message (`#empty-message`) and the chart placeholder (`#chart-placeholder`) are visible if and only if `transactions.length === 0`. Conversely, the transaction list items and the chart canvas are visible if and only if `transactions.length > 0`. These two states are mutually exclusive and exhaustive.

## Testing Strategy

Testing will use manual smoke testing in the browser.

The following scenarios will be checked:
- Add a valid transaction
- Submit with missing or invalid fields
- Add multiple transactions
- Delete a transaction
- Verify total updates after add/delete
- Verify chart updates after add/delete
- Refresh the page and verify localStorage persistence
- Test empty-state behavior
- Test responsive layout at mobile and desktop widths

No automated test framework or test files are required.
